# VoxFlow 剩余开发工作规格

## Problem Statement

VoxFlow 的完成基线已经稳定，但当前产物尚不能作为可持续升级的 Windows/Android 受限测试版分发。发布团队仍缺少组织持有的 Android Release 签名流程、用户可见的数据与隐私说明、双平台成品验收，以及对设置变化可能中断录音、合成或播放这一风险的回归证据。

## Solution

在不重做完成基线的前提下，补齐首个上线版本的发布与验收工作：由 `glosc-ai` 组织统一签署 Android Release APK；在用户提供敏感数据前展示数据与隐私说明；隔离瞬态设置状态与长生命周期语音流程；最后用现有自动化反馈循环、Android 真机和全新 Windows 沙盒共同完成首版测试门槛。

## User Stories

1. 作为 Android 测试用户，我希望安装由 `glosc-ai` 组织正式签名的 APK，以便后续测试版本可以覆盖升级。
2. 作为发布维护者，我希望 Android Release keystore 由组织统一持有，以免个人密钥丢失或多人签名不一致导致升级中断。
3. 作为发布维护者，我希望签名材料只通过 GitHub Actions 组织级 Secrets 注入，以免密钥或密码进入源代码、日志或构建产物。
4. 作为发布维护者，我希望一次发布生成计划约定的各 ABI APK，以便为不同 Android 设备提供对应的测试产物。
5. 作为 Android 测试用户，我希望签名后的应用保持现有应用标识和数据目录，以便升级时保留设置、历史记录和受管音频。
6. 作为 Android 测试用户，我希望在至少一台真机上验证麦克风权限、录音暂停与继续，以便确认硬件交互不是只在构建或模拟环境中成立。
7. 作为 Android 测试用户，我希望在真机上验证文件导入、转录和 TXT/SRT 导出，以便确认文件选择与系统存储交互可用。
8. 作为 Android 测试用户，我希望在真机上验证语音生成、播放、拖动、音量和另存，以便确认音频链路完整。
9. 作为 Android 测试用户，我希望重启应用后仍能看到设置和历史记录，以便确认本地持久化可用。
10. 作为 Windows 测试用户，我希望解压 Release 压缩包即可启动应用，以便在没有 Flutter 开发环境的电脑上测试。
11. 作为 Windows 测试用户，我希望压缩包包含运行所需的 DLL、插件、资源和数据文件，以免因分发文件不完整而启动或运行失败。
12. 作为 Windows 测试用户，我希望在使用未签名测试包前获知可能出现 SmartScreen 警告，以便理解这是受限测试版的已接受限制。
13. 作为 Windows 测试用户，我希望在全新沙盒中完成设置、模型获取、STT、TTS、历史和日志导出流程，以便确认成品不依赖开发机状态。
14. 作为首次使用者，我希望在提供 API Key、文本或音频前看到简明的数据与隐私说明，以便决定是否继续使用。
15. 作为受限测试用户，我希望明确知道 API Key 由平台安全能力加密保存在设备本地，并了解这一保护不等同于防御已控制当前账户或设备的攻击者。
16. 作为受限测试用户，我希望明确知道文本和音频会发送到我配置的 API 服务商，以便理解数据外发边界。
17. 作为受限测试用户，我希望明确知道历史文本和受管音频保存在本机，以及删除历史时受管音频会被删除，以便管理本地数据。
18. 作为受限测试用户，我希望明确知道脱敏日志仍可能包含请求时间、接口路径、模型和错误原因，以便在导出日志前做出知情选择。
19. 作为正在录音的用户，我希望设置页的忙碌状态、提示消息或模型目录刷新不会重置录音，以免丢失当前工作。
20. 作为正在合成语音的用户，我希望设置页的非配置状态变化不会取消合成或清空结果，以免重复提交请求。
21. 作为正在播放语音的用户，我希望设置页的非配置状态变化不会重建播放器或重置播放位置，以免播放被意外中断。
22. 作为修改 API 配置的用户，我希望新的 API Root、API Key 或模型在下一次语音任务中生效，同时不强制终止已经开始的任务。
23. 作为维护者，我希望设置隔离行为由 Provider 组合层回归测试保护，以免未来页面状态修改重新引入核心流程中断。
24. 作为维护者，我希望现有格式检查、静态分析和自动测试始终通过，以便确认发布补缺没有破坏完成基线。
25. 作为维护者，我希望自动测试继续使用伪服务和自定义网络适配器，以免测试消耗真实 API 配额或泄露密钥。
26. 作为发布负责人，我希望每个上线硬门槛都有可核验结果，以便明确判断受限测试版是否允许分发。

## Implementation Decisions

- 完成基线是现状约束。本规格不替换 Flutter/Riverpod/Dio 架构，不重做已有设置、STT、TTS、历史或日志工作流。
- Android 发布遵循“组织发布签名”ADR：使用 `glosc-ai` 组织持有的唯一 Release keystore，从首个上线版本开始保持签名身份连续。
- GitHub Actions 负责 Release 签名构建。keystore、别名和密码来自组织级 Secrets；工作流不得输出密钥内容，并应在任务结束时清理临时签名文件。
- 普通开发和不受信任的变更验证不得获得 Release 签名 Secrets；只有受保护的发布触发方式可以生成正式签名产物。
- Android 应用标识、现有平台兼容范围、应用数据目录和 SQLite 数据契约保持不变。
- Windows 受限测试包是未签名 Release 压缩包，不引入安装器、Windows 代码签名或自动更新。
- 数据与隐私说明必须在首次提交 API Key、文本或音频之前对用户可见。说明至少覆盖 API Key 平台安全存储、数据发送至所配置服务商、本地历史与受管音频、删除行为和脱敏日志字段。
- 数据与隐私说明不引入账户、云同步或复杂同意管理系统；其目标是让受限测试用户在发送敏感数据前知情。
- 网络、STT 和 TTS Provider 只能因其实际运行配置发生变化而刷新。设置页的 `isBusy`、消息、连接结果或模型目录等瞬态状态不得重建正在运行的录音、合成或播放状态。
- API Root、API Key 或模型的有效变更应用于后续任务；已经开始的任务应使用启动时的有效配置完成或按原有错误恢复机制失败。
- 不更改服务端 API 合约、历史数据库结构、受管文件规则或现有日志脱敏边界。
- 首版音色目录保持为 OpenAI 六种标准音色和火山引擎 Seed-TTS 2.0 主表的 93 个常规 Speaker ID；继续以已验证的 `zh_female_cancan_uranus_bigtts` 作为 ByteDance 默认音色。
- 首版上线条件以本规格的自动化结果和两项成品验收记录为准，不能用“构建成功”替代 Android 真机验收或 Windows 成品验收。

## Testing Decisions

- 好测试只验证用户可观察行为和稳定契约，不断言 Provider 实例身份、私有字段或具体重建次数。
- 现有快速反馈循环继续作为基础接缝：格式检查、静态分析和全部自动测试必须通过。已有设置、STT、TTS、历史、日志和响应式界面测试作为先例复用。
- 新增一个主要自动化接缝：使用真实 Riverpod Provider 组合与可控伪服务启动录音、合成或播放状态，再触发设置页瞬态状态变化，断言任务阶段、结果和播放位置不被重置。
- 同一 Provider 组合测试还应验证：真实 API Root、API Key 或模型变更不会中断已开始任务，并会被下一次请求读取。
- 数据与隐私说明在 Widget 层验证，测试用户首次提供敏感数据前能够看到约定内容；测试不依赖具体弹窗、页面或控件结构。
- Android 签名在最终 APK 接缝验证：APK 能通过签名校验、证书指纹与组织预期一致、各 ABI 产物齐全，构建日志和制品中不含签名 Secrets。
- Android 真机验收至少覆盖安装、权限、录音暂停与继续、文件转录、TXT/SRT 导出、TTS 播放与拖动、另存、历史搜索/重播/删除和重启持久化。
- Windows 成品验收在不含 Flutter SDK 和项目源码的全新沙盒执行，至少覆盖启动、设置保存、模型获取、STT、TTS、历史记录、日志导出和重启持久化。
- 自动化测试不得访问真实 OpenAI 或代理 API；真机和沙盒冒烟只使用可撤销、低额度的受限测试密钥，且验收记录不得包含密钥、认证头、输入正文或未脱敏请求体。
- 如果状态隔离回归测试复现核心流程中断，该问题属于上线阻断缺陷；修复后必须重新运行完整首版测试门槛。

## Out of Scope

- 重构或替换完成基线中的架构、状态管理、网络、音频、存储或页面工作流。
- Windows 安装器、Windows 代码签名、自动更新和回滚。
- 公开商店上架材料及公开发布版的完整法律文档。
- 火山 ICL、独立多语种表、S2S、Seed-TTS 1.0 音色，动态音色目录和未验证的服务商专属参数。
- 历史记录分页、虚拟滚动和大数据量性能优化。
- 补齐所有页面边界状态的 Widget 测试或 Android 平台集成自动化测试。
- 为未来 Flutter 工具链升级处理当前不阻断构建的 `record_android` Kotlin Gradle Plugin 警告。
- 解决本机透明代理 Fake-IP 导致的外部 Dart TLS 握手问题。

## Further Notes

- 当前 Android Release 配置仍引用 Debug 签名，且仓库尚无 GitHub Actions 发布工作流，这两项是现有事实而非新架构设计。
- API Key 已从 `SharedPreferences` 迁移到 Windows 当前用户级 DPAPI 或 Android Keystore；旧版明文仅在安全写入并回读验证后删除。
- Windows 未签名压缩包和静态 Seed-TTS 2.0 常规音色目录均为已接受限制，不得在实现过程中扩展为新的发布子项目。
- 最近一次快速反馈循环中，格式检查和静态分析通过，35 项自动测试全部通过；当前没有已复现的核心功能失败。
- 完成本规格的定义是：所有上线硬门槛均有可审计结果，且不存在仍可复现的核心流程阻断缺陷。
